# 01 - Queue & Worker: 실무형 진화 (Evolution)

> 읽는 법: 위에서 아래로 **순서대로**. 각 단계마다
> ① 지금 구조 → ② 무엇이 실제로 깨지는가 → ③ 그래서 다음 단계로.
> 코드(`evolution/S0..S5`)를 실제로 돌리면 그 "깨짐"이 콘솔에 보입니다.
> 용어 자랑 없이, 엔지니어가 현장에서 실제로 내리는 판단만.

---

## 등장하는 구성요소 (먼저 이름만 명확히)

실제 회사 시스템도 결국 이 5개의 조합입니다.

| 이름 | 현실에서 무엇인가 | 한 줄 역할 |
| --- | --- | --- |
| **API Service** | 사용자의 HTTP 요청을 받는 웹 서버 | 요청 받고 **빠르게** 응답해야 함 (producer) |
| **Downstream** | DB, 이메일 게이트웨이, 외부 결제 API 등 | 진짜 일을 하지만 **느리거나 가끔 죽음** |
| **Queue / Broker** | 메모리 큐 → 나중엔 SQS/Kafka 같은 별도 서버 | 일을 잠시 **보관**하는 버퍼 |
| **Worker Service** | 큐에서 꺼내 Downstream을 호출하는 별도 프로세스 | 실제 처리 (consumer) |
| **Autoscaler** | 지표 보고 워커 수를 늘렸다 줄였다 | 부하에 맞춰 **워커 대수** 조절 |

> 핵심 직관: API Service는 "받는 사람", Worker는 "하는 사람", Queue는 그
> 사이의 "받침대". 실무 구조는 이 셋을 **서로 다른 프로세스/서버**로 떼어
> 놓은 것뿐입니다. 코드에서는 스레드로 흉내 내지만, 주석에 "실제로는
> 별도 서버"라고 표시해 두었습니다.

---

## S0 - 큐가 없다 (동기 모놀리식)

**구조**: API Service가 요청을 받으면 그 자리에서 직접 Downstream(이메일
2초)을 호출하고, 끝나야 응답.

**돌려보면**: 요청 1건 응답에 ~2초. 동시에 50건 들어오면 스레드가 묶여
응답이 수 초로 밀리고, Downstream이 잠깐 죽으면 **사용자 요청도 같이
실패**.

**왜 다음으로**: 사용자는 이메일이 가든 말든 "가입 됐다"는 답만 빨리
원함. 일을 **나중에**, **다른 곳에서** 하면 된다는 깨달음.
→ 큐를 도입한다.

**이 단계의 스케일링 요소**: 사실상 없음. 서버를 키워도(scale-up) 느린
Downstream이 그대로라 천장이 낮다.

---

## S1 - 처음으로 큐를 넣다 (인프로세스 큐 + 워커 1개)

**구조**: API Service는 "이메일 보내라"를 **메모리 큐**에 넣고 즉시 응답.
같은 프로세스 안의 백그라운드 워커 스레드 1개가 큐를 비운다.

**돌려보면**: 응답이 2초 → 수 ms. 사용자 체감 즉시 좋아짐.

**무엇이 깨지나**:
- 큐가 **메모리 안**에 있다 → 프로세스가 죽으면 큐의 모든 일이 증발.
- 워커가 처리 중 예외 나면 그 일은 그냥 사라짐(재시도 없음).
- 워커가 1개라 Downstream이 느리면 큐만 쌓임.

**왜 다음으로**: "빠른 응답"은 얻었지만 **일이 사라지는** 건 못 참는다
(가입 메일이 안 감). 잃지 않는 게 다음 목표.
→ 재시도 + 죽은 메시지 격리 + 중복 안전.

**스케일링 요소**: 워커 1개 = 처리량이 워커 1개 속도에 묶임.

---

## S2 - 잃지 않게 만든다 (재시도 + DLQ + 멱등성, 워커 풀)

**구조**: 워커를 풀(여러 개)로. 실패하면 버리지 않고 **간격을 늘려가며
재시도**(한 번에 몰려 Downstream을 두 번 죽이지 않게 약간의 무작위 지연
추가). 정해진 횟수 넘게 실패하면 **따로 빼서 보관(DLQ)** — 나쁜 메시지
하나가 줄 전체를 막지 않게. 같은 일이 두 번 와도 결과가 같게(멱등).

**돌려보면**: Downstream이 잠깐 죽었다 살아나도 일이 안 사라지고
처리됨. 영원히 실패하는 메시지는 DLQ에 격리되어 나머지는 정상.

**무엇이 깨지나**: 큐 크기에 제한이 없다. Downstream이 **오래** 죽어
있으면 큐가 끝없이 커져 결국 메모리가 터진다(장애를 더 키워서 미룬 것).

**왜 다음으로**: "안 잃는다"는 얻었으니, 이제 **시스템이 안 죽게** 해야
한다.
→ 큐 크기 제한 + 가득 차면 밀어내기 + 안전한 종료.

**스케일링 요소**: 워커 여러 개로 처리량 ↑. 단, 아직 한 프로세스 안.

---

## S3 - 시스템이 안 죽게 만든다 (크기 제한 + 밀어내기 + 안전 종료)

**구조**: 큐에 **최대 크기**를 둔다. 가득 차면 두 가지 중 하나:
(A) producer를 잠깐 멈춰 자연히 천천히 받게 하거나, (B) "지금 바쁨"으로
**거절**(웹이면 HTTP 429). 배포로 프로세스를 내릴 때는 새 일 받기를
멈추고 **남은 큐를 다 비운 뒤** 종료(한 건도 안 잃게).

**돌려보면**: producer가 아무리 빨라도 큐 크기가 한계 위로 안 커짐.
배포(종료) 시 처리 중/대기 중 일이 0건 유실.

**무엇이 깨지나**: 한 프로세스 안의 워커 풀은 그 머신 한 대의 CPU가
천장. 트래픽이 더 커지면 큐가 항상 가득 차서 거절만 늘어남.

**왜 다음으로**: 한 대를 키우는 데(scale-up) 한계. **똑같은 워커를 여러
대** 띄워야 한다(scale-out).
→ 큐를 프로세스 밖으로 빼고, 워커를 여러 인스턴스로.

**스케일링 요소**: 큐 크기, 거절 정책, 안전 종료(배포 무중단)의 시작.

---

## S4 - 옆으로 키운다 (별도 Broker + 워커 여러 인스턴스 + Autoscaler)

**구조**: 큐를 **별도 서버(Broker)** 로 분리(현실의 SQS/Kafka 자리).
워커는 이제 **여러 독립 인스턴스**가 같은 큐를 보고 경쟁적으로 가져감
(서로 모름, 그냥 같은 큐를 봄). **Autoscaler**가 큐에 쌓인 양(backlog)을
보고: 길어지면 워커 인스턴스 추가, 짧아지면 제거.

**돌려보면**: 워커 2 → 6으로 늘리면 처리량이 거의 비례해 증가. 부하가
빠지면 워커가 자동으로 줄어 비용 절약.

**무엇이 깨지나**:
- 워커는 늘었는데 모두 **같은 DB**를 두드림 → DB 연결 수가 한계.
  큐는 비는데 DB 에러가 폭증(병목이 옮겨갔을 뿐).
- 워커가 여러 개라 **처리 순서 보장 안 됨**(같은 계좌 입금/출금이 뒤집힘).

**왜 다음으로**: 무작정 워커만 늘리면 안 된다. 옆 부품(DB)의 한계와
**순서 문제**를 다뤄야 한다.
→ 키 기준으로 나누기(파티션) + 워커 동시성 상한.

**스케일링 요소(핵심)**: competing consumers, **무상태 워커**(그래야
복제 가능), backlog 기반 autoscaling, 그리고 "병목은 사라지지 않고
옮겨간다"는 진실.

---

## S5 - 현실 모양 (파티션으로 순서 + 옆 부품 한계 관리)

**구조**: Broker를 **여러 파티션**으로 나눔. 메시지를 키(예: 계좌번호)로
해시해 같은 키는 **항상 같은 파티션** → 그 파티션 안에서는 순서 보장,
서로 다른 키는 다른 파티션에서 병렬. 워커는 파티션을 나눠 맡음.
워커 동시성과 DB 연결 수에 **상한**을 두어 DB를 보호.

**돌려보면**: 같은 계좌의 입출금은 순서대로, 다른 계좌끼리는 병렬로
처리. 처리량 = 파티션 수 × 파티션당 속도. 한 인기 키에 몰리면
**한 파티션만 뜨거워짐**(hot partition)이 보임 → 키 설계가 왜 중요한지
체감.

**여기서 멈춤(과하지 않게)**: 더 들어가면 Kafka 그 자체(모듈 09),
정확히 한 번/사가(모듈 10·11). 이 모듈의 목적은 "큐 하나가 어떻게
실무 구조로 자라는지"를 **끝까지 한 번 보는 것**까지.

**스케일링 요소(핵심)**: 키 기반 파티셔닝(순서 vs 병렬의 타협),
hot partition, 다운스트림 보호(동시성/연결 상한), 처리량 = 파티션 ×
파티션당.

---

## 스케일링 요소 총정리 (이 한 표가 면접 답이다)

| 요소 | 어느 단계 | 한 줄 핵심 |
| --- | --- | --- |
| 비동기 분리 | S1 | 응답 시간과 처리 시간을 떼어 놓는다 |
| 재시도+백오프+무작위 지연 | S2 | 안 잃는다. 단, 다운스트림을 두 번 죽이지 않게 |
| DLQ | S2 | 나쁜 메시지 하나가 줄 전체를 막지 않게 |
| 멱등성 | S2 | "최소 한 번" 전달의 필연 → 두 번 와도 같은 결과 |
| 큐 크기 제한 + 밀어내기 | S3 | 무한 큐는 장애를 키워서 미루는 폭탄 |
| 안전 종료(드레인) | S3 | 배포 중에도 한 건도 안 잃기 |
| 무상태 워커 + competing consumers | S4 | 그냥 복제하면 옆으로 커진다 |
| backlog 기반 autoscaling | S4 | 큐에 쌓인 양이 워커 대수 결정 |
| 병목 이동(DB 연결) | S4 | 워커만 늘리면 병목이 옆으로 옮겨갈 뿐 |
| 키 파티셔닝 | S5 | 필요한 범위만 순서 보장, 나머지는 병렬 |
| hot partition | S5 | 키 설계 잘못하면 한 파티션만 과부하 |
| 다운스트림 보호(상한) | S5 | 큐가 빨라도 DB가 못 버티면 의미 없음 |

---

## 실행 순서

```
cd evolution
java S0_Synchronous.java                 # 큐 없는 고통
java S1_InProcessQueue.java              # 큐 도입, 그러나 유실
java S2_DurableRetryDlq.java             # 안 잃게
java -ea S3_BoundedBackpressure.java     # 안 죽게 (assert로 유실 0 검증)
java S4_ScaleOutAutoscaler.java          # 옆으로 키우기
java S5_PartitionsOrdering.java          # 순서 + 병목/순서 타협
```

각 파일은 마지막에 "무엇이 깨졌고 왜 다음 단계로 가는지"를 콘솔에
직접 출력합니다.
